# onec-mssql2pg

Перенос базы 1С:Предприятия 8 с MS SQL Server на PostgreSQL с коротким окном простоя.

Основной объем данных переливается заранее, пока база работает. В окно попадает только остаток:
изменения за время заливки (через CDC SQL Server), служебные таблицы и сверка. На базе в 600 ГБ окно
заняло около 7,5 минуты, из них 4 минуты сверка.

Утилита написана на Go, один бинарный файл для Windows и Linux. Структуру базы в PostgreSQL по-прежнему
строит платформа 1С (`ibcmd`), утилита переносит только данные.

## Зачем

Штатный путь переезда — `ibcmd infobase replicate` (платформа 8.3.23 и новее) или выгрузка и загрузка `.dt`.
Оба способа переносят базу целиком, и все это время она должна стоять.

На реальной складской базе (MS SQL 2017, ~600 ГБ, 3,27 млрд строк, 1650 таблиц) `ibcmd replicate`:

- переливал данные 15,5 часа;
- упал на построении индексов: PostgreSQL на 64 ГБ памяти не хватило, нужно было 128;
- грузил потоки неравномерно: `ibcmd` держит общий замок, и параллельные потоки ждут друг друга.
  Почти половину базы занимала одна таблица итогов на 11,9 млрд строк.

Нам разрешили простой склада на час. Уложиться в него можно было только одним способом: переносить
данные, пока база работает, а в окне докатить разницу.

## Результат

Та же база, стенд: MS SQL Server на Windows (12 ядер / 24 потока), PostgreSQL (Postgres Pro 1c-18) на
16 vCPU и 128 ГБ, утилита запущена на обоих хостах.

| шаг | `ibcmd infobase replicate` | `onec-mssql2pg` |
| --- | --- | --- |
| перенос данных | 15,5 ч | **23 мин**, база в это время работает |
| индексы | упал (не хватило памяти) | **26 мин**, база в это время работает |
| докатка изменений | нет | **0,4 с** на 43 тыс. изменений |
| служебные таблицы (пользователи, расширения) | вместе со всей базой | **1 мин 20 с**, в окне |
| сверка | нет | **4 мин 18 с**, 1632 из 1632 таблиц совпали |
| окно простоя | весь перенос | **~7,5 мин** |

Платформа 8.5 открыла базу, залитую утилитой. Контрольные запросы прочитали 114 млн документов, даты
совпали с источником. Построчная сверка на другой базе (4686 таблиц) совпала с эталоном `ibcmd`, отличается
только служебная колонка `_version`.

## Как это устроено

1. **Структуру строит платформа.** По `sys.*` источника собирается пустая база-заготовка в MS SQL, в нее
   копируются служебные таблицы (`Config`, `Params`, `v8users`, `DBSchema`…). `ibcmd infobase replicate`
   переносит пустую заготовку в PostgreSQL за секунды, и оттуда же берутся DDL таблиц (pre-data) и индексов
   (post-data). Служебные таблицы при этом переходят в формат новой платформы.
2. **Заливка данных.** Утилита читает большие таблицы частями параллельно. Разбиение идет по кластерному
   ключу: колонки с одним значением становятся условием равенства, колонки, где значений не больше 64, делятся
   по значениям, остальные по квантилям выборки. Все части одной таблицы сходятся в **один**
   `BEGIN; TRUNCATE; COPY … (FORMAT binary, FREEZE); COMMIT`. При `wal_level=minimal` PostgreSQL не пишет WAL
   для таблицы, очищенной в той же транзакции, а `FREEZE` сразу замораживает строки, поэтому массовой заморозки
   автоочисткой после заливки не будет.
3. **Индексы** строятся параллельно по таблицам, первичный ключ первым.
4. **Докатка.** На время переноса на источнике включается CDC. Утилита берет итог изменений по уникальному
   ключу и применяет его в PostgreSQL одной транзакцией вместе с отметкой LSN: `DELETE … USING` плюс `INSERT`.
   Повторный запуск безопасен, поэтому докатку можно гонять циклом до самого окна.
5. **Сверка.** Число строк по всем таблицам сравнивается с источником, а для приемки есть построчное
   сравнение с эталонной базой.

Преобразования MS SQL → PostgreSQL сверены построчно с `ibcmd`:

| MS SQL | PostgreSQL | заметка |
| --- | --- | --- |
| `datetime2` со сдвигом `_YearOffset` | `timestamp` | сдвиг (обычно 2000 лет) есть и в служебных `config`, `configcas` |
| `binary(1)` | `boolean` | |
| `binary(n)`, `varbinary`, `image` | `bytea` | |
| `nvarchar`, `nchar`, `ntext` | `mvarchar`, `mchar` | в двоичном COPY это UTF-16LE, перекодировки нет |
| `numeric` | `numeric` | двоичный формат PG |
| `timestamp` (rowversion, `_version`) | `int4` | ставится 1, как у `ibcmd` |

## Сравнение с ibcmd

| | `ibcmd infobase replicate` | `onec-mssql2pg` |
| --- | --- | --- |
| что переносит | всю базу, включая структуру | только данные таблиц `_*`; структура и служебные таблицы — через `ibcmd` по пустой заготовке |
| параллельность | общий замок, потоки ждут друг друга | части таблиц читаются независимо, запись без WAL |
| перенос без остановки базы | нет | да: снимок базы (`CREATE DATABASE … AS SNAPSHOT`) и CDC |
| окно простоя | весь перенос | докатка, служебные таблицы, сверка |
| память PostgreSQL | индексы падали на 64 ГБ | индексы строятся отдельным шагом, по таблицам |
| где запускать | только Windows (MS SQL как источник), нужен SQL Server Native Client | Windows или Linux, несколько хостов сразу (`-shard K/N`) |
| проверка результата | нет | сверка числа строк, построчное сравнение |
| поддержка | вендор | эта утилита, проверена на одной конфигурации (см. ограничения) |

## Сценарий переезда

Кратко (подробно, с командами — [docs/migration.md](docs/migration.md)):

**Заранее, база работает.**
1. Собрать базу-структуру: DDL из MS SQL, заготовка, `ibcmd` → PostgreSQL. Из нее — целевая база без индексов.
2. `prepare` на PostgreSQL: `wal_level=minimal`, `fsync=off`, автоочистка выключена. База еще не боевая:
   при сбое ее просто льют заново.
3. Включить CDC на источнике и снять снимок базы.
4. Залить данные из снимка, построить индексы.
5. Гонять докатку циклом.

**Окно.**
6. Запретить работу в базе (сеансы, регламентные задания).
7. Последняя докатка. Перелить таблицы без уникального ключа (их не докатить) и служебные таблицы
   (пользователи, расширения на момент запрета).
8. Сверка, `restore` настроек PostgreSQL, `ANALYZE`.
9. Перевести регистрацию базы в кластере 1С на PostgreSQL и разрешить работу.

**После.** Выключить CDC на источнике, удалить снимок, сделать бэкап PostgreSQL.

## Режимы

| `-mode` | что делает |
| --- | --- |
| `plan` | показать таблицы к переносу и разбиение на части |
| `copy` | заливка (`-shard K/N` и `-phase load` — на нескольких хостах; `-nokey` — только таблицы без уникального ключа) |
| `ddl` | выполнить файл DDL (индексы) параллельно по таблицам: `-ddl post-data.sql -workers 10` |
| `delta` | докатка изменений CDC (`-loop N` — повторять каждые N секунд) |
| `cdc-enable`, `cdc-disable` | включить или выключить CDC на всех таблицах; блокировку ждет `-lock-timeout`, дальше круги повтора |
| `verify-counts` | сверка числа строк с источником |
| `verify-pg` | построчное сравнение двух баз PostgreSQL (`PG_REF_DSN` — эталон) |
| `prepare`, `restore` | перевести PostgreSQL в режим заливки и вернуть прежние настройки (они хранятся в `-state`) |

Подключения задаются переменными окружения:

```
MSSQL_DSN=sqlserver://user:password@host:1433?database=base&encrypt=disable&packet+size=32767
PG_DSN="host=pg-host user=postgres dbname=base sslmode=disable password=..."
```

Таблицы отбираются регулярками по именам PostgreSQL: `-only`, `-exclude`. Например, переносить только
данные 1С без служебных: `-exclude '^[^_]|^_yearoffset$'`.

## Сборка

```
go build -o onec-mssql2pg .
GOOS=linux go build -o onec-mssql2pg .
```

В `scripts/` лежит обвязка сценария: генератор DDL заготовки, сборка базы-структуры, подготовка целевой базы,
смена СУБД в регистрации базы. Скрипты рассчитаны на Windows-хост с SQL Server и `ibcmd` и на Linux-хост
с PostgreSQL. Параметры площадки передаются аргументами.

## Ограничения

- Проверено на одной конфигурации (складская, платформа 8.3.18 на источнике, 8.5.1 на цели),
  MS SQL Server 2017 и 2022, Postgres Pro 1c-18. На других конфигурациях начинайте с `verify-pg`
  против эталона `ibcmd` на копии.
- CDC нужен на источнике на время переноса. На таблице с CDC запрещен `TRUNCATE`: платформа 8.3.18 за час
  штатной работы не сделала ни одного (проверено сессией Extended Events), но на своей базе это стоит проверить.
- Таблицы без уникального индекса CDC не докатывает: утилита переливает их целиком в окне (`-nokey`).
- `prepare` выключает `fsync`. До `restore` база не защищена от сбоя питания, и это осознанный выбор:
  при сбое ее заливают заново.
- Около половины процессора утилиты уходит на разбор строк драйвером `go-mssqldb`: он создает объект на каждое
  значение. Это главный резерв ускорения.
